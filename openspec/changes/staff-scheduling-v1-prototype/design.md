## Context

`staff-scheduling` 是 `api-specs` 專案中最初期的一個，從初始化提交後沒有任何後續規劃；`openapi.yaml` 的 `paths: {}`、`Employee`/`Shift` schema 皆為空殼。使用者描述的核心場景是預約式排班：後台為人員與客戶建立預約（人員＋客戶＋時段），人員與客戶可各自透過 App 查看（及取消）自己的預約。與使用者討論後確認 v1 prototype 採最小可行範圍：預約時段必須綁定特定客戶（非純上班時段）、人員帳號僅由後台建立、客戶可自助註冊、只有新增與取消兩種操作。

## Goals / Non-Goals

**Goals:**
- 後台使用者可以新增人員帳號，人員憑此帳號登入自己的 App。
- 客戶可以在 App 自行註冊帳號。
- 後台使用者可以選擇人員、客戶、時段建立一筆預約。
- 建立預約時檢查同一人員、同一客戶是否已有時段重疊，兩者皆不可重複排程。
- 後台使用者可以取消任一筆預約；客戶可以取消自己的預約。
- 人員登入 App 可查看自己名下的班表（唯讀）。
- 客戶登入 App 可查看並取消自己名下的預約。

**Non-Goals:**
- 不做修改/改期既有預約，v1 只有新增與取消。
- 不做人員自行調整班表、請假排休。
- 不做通知/提醒功能。
- 不做預約取消時間限制（例如開始前 X 小時內禁止取消）。

## Decisions

### 1. 預約時段必須綁定特定客戶（預約制，而非純上班時段）
後台建立的每一筆排班時段都必須指定客戶，形成「人員＋客戶＋時段」的預約（Appointment），而非單純記錄人員的上班時間。
- **原因**：使用者明確要求排班時段需綁定客戶，核心場景是類似美容院/家教等一對一預約服務，而非單純的員工排班表。
- **考慮過的替代方案**：不綁定客戶的純班表模式——放棄，不符合使用者描述的預約制場景。

### 2. 人員帳號由後台建立，人員不可自行註冊；客戶可自行註冊
人員帳號（手機＋密碼）僅能由後台使用者新增，且新增時同時設定初始密碼；客戶則可在 App 自行註冊帳號。
- **原因**：人員是服務提供方，身分需要後台先行把關；客戶是服務對象，降低使用門檻、允許自助註冊更符合一般預約系統的慣例。
- **考慮過的替代方案**：人員與客戶皆由後台建立，或皆可自行註冊——放棄，使用者明確做出不對稱的選擇（人員後台建立、客戶自助註冊）。

### 3. 雙重時段衝突檢查：同一人員與同一客戶皆檢查，且排除已取消的預約
建立預約時，系統需檢查「同一人員」與「同一客戶」是否已有時段重疊的既有預約，兩者只要有一個重疊即不可建立；檢查範圍排除 `status` 為 `cancelled` 的預約。
- **原因**：避免同一人員被重複排班、也避免同一客戶同時段有兩筆預約（例如誤植或重複預約）；排除已取消的預約是因為使用者明確要求取消後的時段應視為可再排。
- **考慮過的替代方案**：只檢查同一人員的時段重疊（不檢查客戶）——放棄，使用者明確要求兩者皆需檢查。

### 4. 取消權限：後台可取消任一筆，客戶可取消自己的，人員無取消權限
人員只能查看自己的班表（唯讀），不能取消或修改任何預約；取消權限僅開放給後台使用者（任一筆）與客戶（僅自己的）。
- **原因**：人員是服務執行方，取消預約屬於後台或客戶（服務需求方）的決定，不應由人員單方面變動。
- **考慮過的替代方案**：開放人員也能取消自己的預約——放棄，使用者明確將取消權限限定在後台與客戶。

### 5. 人員與客戶共用同一支 App，後台使用者使用獨立 Web 後台
人員與客戶登入同一支 App，依登入身份顯示對應角色能看到的內容；後台使用者則使用獨立的 Web 後台（非 App），不與人員/客戶共用介面。
- **原因**：人員與客戶的功能高度相似（皆為「查看自己的預約」），共用一支 App 可降低開發成本；後台使用者的操作（新增人員、建立/取消預約）與終端使用者性質不同，獨立 Web 後台便於管理與權限隔離。

### 6. 認證方式：沿用既有 bearerAuth（JWT），不另起 Web session 機制
後台 Web、人員 App、客戶 App 的 API 驗證皆沿用 `api-specs/projects/staff-scheduling/openapi.yaml` 既有的 `bearerAuth`（JWT）機制。
- **原因**：避免引入額外的認證機制複雜度，JWT 可同時滿足 Web 後台與 App 的驗證需求。

## Risks / Trade-offs

- **[風險] 人員帳號的初始密碼由後台建立時直接設定，若傳遞方式不安全可能外洩** → 緩解：v1 僅要求密碼雜湊儲存；初始密碼的安全傳遞方式（例如簡訊通知、首次登入強制改密碼）留待實作階段規劃，v1 不強制要求。
- **[風險] 客戶自助註冊沒有身分驗證機制，可能產生虛假帳號** → 緩解：v1 範圍不含身分驗證（如簡訊驗證碼），此風險需在後續版本視需求補強。
- **[風險] 取消預約後若要重新排定同一時段，需仰賴「排除已取消預約」的衝突檢查邏輯正確無誤，否則可能誤判衝突或遺漏衝突** → 緩解：此邏輯已明確列入 Requirement 與 Scenario（見 specs），實作與測試階段需特別驗證邊界情況（例如取消後同一時段立即被其他客戶預約）。
- **[取捨] v1 不支援修改/改期，使用者若要異動預約時段，必須先取消再重新建立** → 權衡：降低 v1 的狀態機複雜度；改期功能列入後續版本待辦。

## Migration Plan

1. 實作 `Employee`、`Customer`、`Appointment` 的資料模型與對應的 API endpoint（後台 Web、人員 App、客戶 App 三組）。
2. 先驗證後台可建立人員帳號（含初始密碼），人員可用該帳號登入 App 查看自己的班表（此時應為空列表）。
3. 驗證客戶可在 App 自行註冊。
4. 驗證後台建立預約（選人員、客戶、時段）後，該預約同時出現在對應人員與客戶的 App 班表中。
5. 驗證時段衝突檢查：對同一人員或同一客戶的重疊時段建立預約時被拒絕；取消預約後，該時段可再次被排入新預約。
6. 驗證取消流程：後台可取消任一筆預約；客戶可取消自己的預約；人員無法執行取消操作。
7. **Rollback**：本次為全新能力（`staff-scheduling` 原本無任何實作），若需回退，直接停用新增的 API endpoint 與前端頁面即可，不影響其他專案。
