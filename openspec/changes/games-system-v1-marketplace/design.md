## Context

`games-system` 是五個 `api-specs` 專案中最初期的一個，從初始化提交後沒有任何後續規劃；`openapi.yaml` 的 `paths: {}`、`Game`/`Session` schema 皆為空殼。使用者描述的核心場景是一個三方遊戲平台：營運方管理商戶、商戶上架自己的遊戲、玩家匿名瀏覽並遊玩已上架的遊戲。與使用者討論後確認 v1 prototype 採最小可行範圍：單一審核結果（通過）、最簡化的上架欄位、玩家完全匿名、遊戲以 iframe 嵌入商戶提供的外部網址。

## Goals / Non-Goals

**Goals:**
- 營運後台可以建立商戶帳號，商戶憑此帳號登入自己的後台。
- 商戶可以上架遊戲（名稱 + 外部遊戲網址），送出後進入待審核狀態。
- 營運後台可以審核待審核的遊戲，通過後對外公開上架。
- 玩家不需登入即可瀏覽已上架遊戲列表、進入遊戲（iframe 嵌入）、離開回到列表。
- 玩家每次進入/離開遊戲都留下一筆 Session 記錄（進入時間、離開時間），即使玩家本身匿名無身分。

**Non-Goals:**
- 不做審核駁回流程，v1 只有「通過」一種審核結果。
- 不做遊戲下架功能，上架後永久顯示。
- 不做遊戲分類、縮圖、描述等豐富上架欄位，v1 只有名稱與外部網址。
- 不做玩家帳號與登入機制。
- 不做商戶編輯或撤回已送出的上架申請。
- 不做任何基於 Session 資料的報表/統計 API，v1 只記錄原始進入/離開時間。
- 不處理營運後台使用者自身的帳號建立流程，假設為既有/預先建立。

## Decisions

### 1. 商戶帳號由營運後台建立，商戶不可自行註冊
商戶帳號（username + 密碼）僅能由營運後台使用者新增，商戶沒有自助註冊入口。
- **原因**：使用者明確要求「只有商戶後台才能申請上架遊戲」，且商戶身分需要營運方先行把關（例如合作關係確認），自助註冊不符合平台的商業邏輯。
- **考慮過的替代方案**：商戶自行註冊、待審核通過才能使用——放棄，使用者明確選擇由營運後台建立帳號的模式，且與同 repo 的 `staff-scheduling` 專案一致（人員帳號也是由後台建立）。

### 2. 審核結果 v1 僅有「通過」，不做「駁回」
商戶送出的上架申請，營運後台只能將狀態從「待審核」轉為「已上架」，沒有駁回狀態與駁回原因紀錄。
- **原因**：使用者明確表示 v1 先只做通過，駁回留到後續版本，降低 v1 的狀態機複雜度。
- **風險**：待審核清單會持續累積未通過但也沒有被明確拒絕的項目，長期需要駁回機制補上（見 Open Questions）。

### 3. 遊戲頁面以 iframe 嵌入商戶提供的外部網址
玩家點擊遊戲後，前端以 iframe 嵌入商戶上架時填寫的 `externalUrl`，平台本身不代管遊戲內容。
- **原因**：使用者明確選擇「嵌入商戶提供的外部遊戲網址（iframe）」，遊戲內容本身由商戶自行託管，平台只負責上架審核與流量導引。
- **風險**：iframe 嵌入可能受限於外部網站的 `X-Frame-Options`/CSP 設定而無法嵌入——此為實作階段需驗證的風險，v1 範疇不含因應措施（例如改為跳轉）。

### 4. 玩家匿名，但仍建立 Session 記錄進入/離開時間
玩家不需登入即可瀏覽與遊玩，但系統仍在玩家進入與離開遊戲時各建立一筆 Session 記錄時間戳記，不綁定任何使用者身分。
- **原因**：使用者希望玩家完全匿名（降低遊玩門檻），但仍需要保留基礎的遊玩記錄（`Session` schema 原本就存在於骨架中），供後續版本做流量分析或商戶對帳使用。
- **考慮過的替代方案**：完全不記錄 Session，純前端行為——放棄，使用者明確要求需要記錄每次進入/離開的時間。

### 5. 商戶後台「遊戲列表」僅顯示自己上架的遊戲
商戶登入後只能看到自己名下的 `Game` 記錄（含待審核與已上架狀態），看不到其他商戶的遊戲。
- **原因**：這是後台權限隔離的基本假設，避免商戶看到競爭對手的上架資訊；原始需求「商戶只有登入、上架遊戲、遊戲列表」隱含此列表是商戶自己的管理範圍。

### 6. 前端玩家列表只顯示「已上架」狀態的遊戲，不分商戶
前端公開頁面彙整所有商戶的已上架遊戲，以單一列表呈現，不依商戶分類或篩選。
- **原因**：v1 不做分類/篩選欄位（見 Non-Goals），玩家視角只需要一個統一的已上架遊戲列表。

## Risks / Trade-offs

- **[風險] 審核只有「通過」沒有「駁回」，待審核清單會持續累積不會被處理的項目** → 緩解：v1 先接受此限制，列為後續版本待辦（見 Open Questions）。
- **[風險] iframe 嵌入外部網址可能被目標網站的 `X-Frame-Options` 或 CSP 阻擋，導致遊戲頁面空白** → 緩解：v1 不處理，實作階段需以商戶實際提供的網址驗證可行性，必要時於後續版本改為跳轉而非嵌入。
- **[風險] 密碼以雜湊儲存，但 v1 未定義密碼強度、重設密碼等機制** → 緩解：v1 僅要求密碼雜湊儲存，不公開明文；重設密碼流程留到後續版本。
- **[取捨] 玩家完全匿名，Session 記錄無法對應到特定玩家身分，限制了未來依玩家維度分析的可能性** → 權衡：符合使用者「降低遊玩門檻」的明確要求，之後若要加玩家身分，需另外設計遷移方案（例如選擇性登入）。
- **[取捨] 遊戲上架後無法下架，若商戶提供的外部網址失效或內容不當，平台沒有即時處理手段** → 權衡：v1 範圍明確排除下架功能，此風險需在後續版本優先處理。

## Migration Plan

1. 實作 `Merchant`、`Game`、`Session` 的資料模型與對應的 API endpoint（營運後台、商戶後台、玩家前端三組）。
2. 先驗證營運後台可建立商戶帳號、商戶可用該帳號登入商戶後台。
3. 驗證商戶上架遊戲（名稱 + 外部網址）後，狀態為「待審核」，且只出現在該商戶自己的遊戲列表中。
4. 驗證營運後台審核通過後，該遊戲狀態變為「已上架」，並出現在玩家前端的公開列表中。
5. 驗證玩家前端可匿名瀏覽已上架遊戲列表、點擊進入 iframe 嵌入頁面、點擊離開回到列表，且進入/離開各建立一筆 Session 記錄。
6. **Rollback**：本次為全新能力（`games-system` 原本無任何實作），若需回退，直接停用新增的 API endpoint 與前端頁面即可，不影響其他專案。

## Open Questions

- 審核駁回流程：後續版本何時加入「駁回」狀態與駁回原因紀錄？
- 遊戲下架機制：後續版本是否開放商戶自行下架，或僅營運後台可強制下架？
- 遊戲上架欄位是否需要擴充（分類、縮圖、描述），以及擴充的優先順序？
- iframe 嵌入外部網址若被目標網站阻擋，後續版本的因應方式（跳轉 vs. 要求商戶提供可嵌入的網址）？
- Session 資料未來是否需要報表/統計 API，以及資料保留期限？
- 密碼重設、帳號停用等商戶/營運帳號管理的周邊機制，何時納入規劃？
