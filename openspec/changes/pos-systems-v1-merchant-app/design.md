## Context

`pos-systems` 的營運後台已實作（管理員登入/登出、商家列表查詢），但商家端 App（Electron，部署於樹莓派、商家區域網路）完全尚未實作。原始範疇來自 commit `267b253 feat: pos-system` 的描述：「商家 App：員工登入與登出、新增商品（先以關東煮店為基礎）、結帳功能、連線出單機」。本次補上正式規格，對原描述沒有細節的地方先以 v1 最小化、最保守的選項拍板，降低開發與依賴複雜度。

## Goals / Non-Goals

**Goals:**
- 員工可以登入/登出商家 App。
- 員工可以新增商品、查詢商品列表。
- 員工可以選擇商品建立訂單並以現金完成結帳。
- 結帳完成後可連線區域網路內的出單機列印收據。

**Non-Goals:**
- 不做商品編輯、刪除（v1 僅新增與查詢）。
- 不整合信用卡/第三方金流（v1 僅現金）。
- 不做雲端列印服務（v1 僅區網內直連出單機）。
- 不處理營運後台「商家連線狀態」獨立機制（已另外列為 v2 待辦）。

## Decisions

### 1. 商品管理範圍：僅新增與查詢，不支援編輯/刪除
v1 的商品管理僅提供「新增商品」與「查詢商品列表」兩個操作。
- **原因**：比照其他專案 v1 最小化原則（例如 games-system v1 的遊戲上架也不支援編輯/下架），優先把核心流程（結帳）打通，商品資料的維運需求留待實際使用後再評估。
- **考慮過的替代方案**：完整 CRUD——放棄，v1 尚不清楚商品資料的實際維運頻率，先以最小功能驗證流程可行性。

### 2. 結帳付款方式：僅現金，不整合第三方金流
v1 結帳僅支援現金收款，不整合信用卡或第三方支付閘道。
- **原因**：商家 App 部署在區域網路、樹莓派環境，第三方金流整合涉及額外的網路依賴（需對外連線）與金鑰管理複雜度，與「先把核心流程打通」的 v1 目標不符。
- **考慮過的替代方案**：整合綠界等金流服務——放棄，留待後續版本視商家實際需求評估。

### 3. 出單機連線方式：區域網路內直連 ESC/POS 相容出單機
結帳完成後，系統透過區域網路直接連線 ESC/POS 相容的出單機（IP + Port）觸發列印，不透過雲端列印服務。
- **原因**：商家 App 本身就部署在商家區域網路內（樹莓派），出單機通常也在同一網路，直連是最簡單、不需額外依賴雲端服務的做法，符合「先用最簡單方式打通」的原則。
- **考慮過的替代方案**：透過雲端列印服務（例如 Google Cloud Print 類似方案）——放棄，增加對外網路依賴與服務依賴，不符合本地部署場景。

### 4. 員工登入：沿用既有 bearerAuth（JWT）機制
商家 App 的員工登入/登出與既有營運後台一樣，使用 JWT bearer auth 驗證 API 請求。
- **原因**：避免引入第二套認證機制，降低維運複雜度；既有 `openapi.yaml` 已定義 `bearerAuth`，可直接沿用。

## Risks / Trade-offs

- **[風險] 現金結帳沒有金流紀錄可供對帳，僅能依賴系統內的 Order/Payment 記錄** → 緩解：v1 要求每筆結帳都建立對應的 `Order` 與 `Payment` 記錄，供人工對帳使用；電子支付對帳留待後續版本整合金流後處理。
- **[風險] 出單機直連依賴區域網路穩定性，若出單機離線或網路異常，結帳可能完成但收據列印失敗** → 緩解：v1 要求結帳與列印為兩個獨立步驟，列印失敗不影響結帳成功（訂單與付款已記錄），列印狀態記錄在 `Receipt.printerStatus`，供後續人工補印。
- **[取捨] 不支援商品編輯/刪除，上架錯誤的商品只能留著或靠後續版本補救** → 權衡：v1 優先驗證結帳流程本身，商品維運需求留待實際使用後再評估優先序。

## Migration Plan

1. 實作 `Product`、`Order`、`Payment`、`Receipt`、`EmployeeSession` 資料模型。
2. 實作員工登入/登出 API（沿用 bearerAuth）。
3. 實作新增商品、查詢商品列表 API。
4. 實作結帳 API：選擇商品建立訂單、計算總金額、現金收款建立 Payment 記錄。
5. 實作出單機連線列印：結帳成功後觸發列印，列印失敗不回滾訂單與付款。
6. 於商家 App（Electron）串接上述 API，於樹莓派環境進行端到端驗證（含實體出單機連線測試）。
7. **Rollback**：本次為全新能力，若需回退，直接停用新增的 API endpoint 與 Electron App 的對應頁面即可，不影響既有營運後台功能。

## Open Questions

- **員工帳號由誰建立、如何設定初始密碼？** repo 裡目前沒有「商家端員工帳號管理」的既有慣例可參考（不像 `staff-scheduling`/`games-system` 已經決定由後台建立）。需要使用者確認：是店長自行在商家 App 建立員工帳號，還是比照營運後台模式、由營運後台統一建立商家員工帳號？這點會影響是否需要新增「員工帳號管理」API 與對應角色權限設計。
