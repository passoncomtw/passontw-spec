## Context

`p2p-exchange-service`（幣安 C2C 平台）目前只有 `Order`、`Trade` 的 schema stub（欄位皆「內容後續補充」），`openapi.yaml` 的 `paths` 為空。經 explore 討論確認終局目標是仿 Binance C2C 的完整流程，但分三版逐步建立。本設計是三版路線圖的第一版：使用者對使用者、角色對稱、含託管凍結的交易能力。

## Goals / Non-Goals

**Goals:**
- 任一使用者可建立掛單、對他人掛單下單，完成含託管凍結的完整交易生命週期：建立掛單 → 下單成交並凍結 → 標記已付款 → 確認收款並放幣 → 完成；或取消/逾時解除凍結。
- 支援多幣種/多代幣交易對。
- 資料模型設計為 V2（買賣角色分工＋廣告掛牌）與 V3（爭議仲裁）預留擴充空間，避免日後破壞性改版。

**Non-Goals（刻意排除，記錄路線圖以避免未來重新討論）：**
- V2 才做：廣告/掛牌上架資源、買賣角色固定分工（賣家專屬上架、買家專屬瀏覽下單），對應「平台對使用者」的角色明確化方向。
- V3 才做：爭議/申訴、客服仲裁狀態機。
- 本版不支援部分成交（一張 Order 是否可被多筆 Trade 拆單），留待 V2 依實際需求決定。
- 不整合實際金流/銀行 API，僅記錄「已標記付款」狀態。

## Decisions

1. **沿用既有 `Order` + `Trade` 兩個實體，不新增 Ad/Listing schema**
   - 理由：V1 角色對稱，掛單本身即完整表達交易意願，尚不需要獨立的「廣告」概念；等 V2 買賣角色分工明確後才需要。
   - Trade-off：V2 導入 Ad 資源時需新增關聯欄位，但因 V1 已避免把角色欄位寫死，遷移成本可控。

2. **`Order`（掛單意願）與 `Trade`（成交後資金流轉）分離為兩個狀態機**
   - `Order` 狀態：上架中 → 已成交 / 已下架
   - `Trade` 狀態：待付款 → 待確認收款 → 已完成；或 → 已取消
   - 理由：一個 Order 未來可能對應多筆 Trade（部分成交，V2+ 再決定），現在分離可避免日後拆分作業。

3. **託管凍結於建立 `Trade` 時觸發，而非建立 `Order` 時**
   - 理由：Order 只是單方意願，尚未有對手方前不應凍結資產；雙方都同意（成交／建立 Trade）才代表需要託管保障。

4. **角色欄位用「掛單方／下單方」而非「買家／賣家」命名**
   - 理由：V1 角色對稱，避免使用會暗示固定角色的語彙；為 V2 導入 `sellerId`/`buyerId` 保留欄位擴充空間，不必重構既有欄位。

## Risks / Trade-offs

- **[風險] 無爭議機制（V3 才做）** → 若收款方惡意不確認收款，付款方資產可能卡在「待確認收款」。
  → **緩解**：設定合理逾時時間，逾時未確認時，Trade 依「逾時自動取消」規則解除凍結歸還掛單方資產；V1 不做「該由誰負責」的仲裁判斷。

- **[風險] 不支援部分成交** → 大額掛單的流動性較差。
  → **緩解**：先觀察 V1 實際使用情況，需要再於 V2 評估是否支援拆單。

- **[風險] 多幣種但無即時匯率/流動性驗證** → 可能建立無意義或無法達成的幣種對掛單。
  → **緩解**：V1 先以固定的可交易幣種白名單做基本驗證，不做即時匯率或流動性檢查。
